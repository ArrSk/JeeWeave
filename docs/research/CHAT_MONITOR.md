> 2026-10-18 最新状态：用户要求暂停开发。侧栏及插件管理已隐去入口，本机接收被停用；原代码、单测、历史数据和本页研究保留。下面接入步骤是先前阶段记录，目前不能在产品界面开启。

调研日期：2026-10-18。目标是把通知整理成可核对的事项；当前先完成 Desktop 的接收与整理层。Web 客户端不变。以下均为项目方资料和实际本地实现，真实登录能力另行验收。

## 2026-10-18 新方向：正常登录官方 QQ，减少额外配置

用户认为 NapCat/OneBot 的安装配置负担过大，要求重新调研，优先“只正常登录 QQ”。下面是本次新增的候选方向，覆盖文末此前以外部登录端联调为主的下一步建议；已经实现的上报接口保留为兼容入口，**以下路线尚未在本机 QQ 验证或实现**。

| 路线 | 案例与核实依据 | 符合正常登录的程度 | 关键边界 |
| --- | --- | --- | --- |
| Windows 通知读取 | [QQListener](https://github.com/BSOD-MEMZ/QQListener)、其 [开发说明](https://github.com/BSOD-MEMZ/QQListener/blob/main/DEVELOPMENT.md)区分 WinSDK 系统通知与 UIA 通知窗口捕获；[微软通知监听文档](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/notification-listener)提供正式能力 | 高，普通 QQ 登录后读取它交给系统的通知 | QQ 必须实际产生可读取的通知，通知关闭、隐藏内容、聊天当前激活等情况需实测；只能保证获取系统可见内容，不保证全文或每条消息 |
| QQ 聊天窗口无障碍读取 | [QQSafeChat](https://github.com/TheD0ubleC/QQSafeChat)绑定聊天控件，文档说明窗口遮挡/焦点和部分环境需开启 accessibility；[微软 UIA 文档](https://learn.microsoft.com/en-us/windows/win32/winauto/entry-uiauto-win32)说明客户端通过控件属性访问界面 | 高，使用原 QQ 登录会话；部分版本可能需要一次性启动参数 | 取决于 QQ 暴露的控件，当前打开/已加载消息不等于全部群历史；最小化、锁屏、窗口切换和快速刷屏都需本机验收 |
| 截图 OCR | 对指定聊天区域作本地文字识别，作为技术备选，未选定项目或实测 | 使用普通 QQ，但窗口必须能被正常捕获 | 图片里的文字不是消息数据库；存在识别、时间/发送者关联、遮挡和漏行问题，不作为优先方案 |
| QQ 插件或内置运行时加载 | [LiteLoaderQQNT](https://github.com/LiteLoaderQQNT/LiteLoaderQQNT)、[cinlan-qq-bot](https://github.com/lianyorker/cinlan-qq-bot) | 表面复用官方登录，但仍涉及插件/加载器/专门启动 | 不符合本轮尽量保持普通客户端使用方式；LiteLoader 主仓库已归档，Cinlan 文档也说明不能直接附着已经普通启动的 QQ。本轮不引入 |
| 官方机器人 | [腾讯 BotGo](https://github.com/tencent-connect/botgo)说明创建机器人、凭据与事件回调流程 | 需要机器人接入，并非普通个人 QQ 登录即订阅全部群 | 不把机器人开发者能力等同为个人客户端的通用群消息 API；本次没有找到满足后一种体验的现成官方接口 |

**建议作为待验证的主路线：系统通知捕获，聊天窗口读取用于用户主动补取全文。** 用户目标体验是正常登录 QQ，在几微授权消息读取、选择目标群，后台通知先进入既有收件箱；需要完整上下文时主动打开群，再由只读窗口适配尝试获取。这里的“建议”是对官方能力和案例的工程判断，不是已实现承诺。

先做有边界的本机兼容性诊断：仅针对用户指定 QQ/测试群，确认 QQ 是否投递系统通知、是否暴露窗口文字，输出可用/摘要/不可读的状态；不先搭建完整监测器、不扫描全部聊天资料。之后验证接收时机、长文、合并通知、同名群、最小化、窗口切换与恢复。

通知常只有群/发送者显示名，不能假定带真实群号、发送者 QQ 号或原消息时间。后续需要独立的观察事件格式和用户确认的群映射，记录采集时间/来源类型并标注摘要；不能伪造 OneBot ID 或把不确定来源直接匹配到同名群。通知被截断时不自动当成完整课程或截止事项。

集成 Windows 正式通知 API 还需能力清单和用户授权，当前 Electron 文件夹版尚未验证打包/授权方案；UIA 通知捕获可作为另一条检测分支，不能把它与正式 API 的授权/可靠性混称。QQListener 文档可提供分层参考，但其示例不代替微软要求。Context7 工具仍不可调用，**未完成 Context7 查询**；本轮仅读公开资料，没有安装或启动下载的项目、访问真实 QQ 窗口或改客户端配置。

## 2026-10-18 补充需求：历史聊天、群公告和群文件

用户进一步要求读取以上三类内容，仍希望正常登录官方 QQ。这使目标从新通知整理扩展为“指定群的内容采集”；通知监听只能承担新增提醒，不能单独解决历史/公告/文件。

| 内容 | 普通 QQ 路线的候选设计（未实现/未实测） | 必须说明的范围 |
| --- | --- | --- |
| 历史聊天 | 用户选择群和日期范围，打开聊天记录页；尝试通过控件读取、滚动加载与去重，或导入用户主动提供的记录 | 只处理账号实际可加载的记录；需验证时间/发送者关联、分页覆盖和缺口，不能承诺全部历史或恢复已不可访问的消息 |
| 群公告 | 用户打开公告列表/详情，尝试提取页面公开给无障碍接口的标题、正文及可见发布信息；必要时主动复制/截图导入 | 列表摘要与详情全文分开；图片公告需要 OCR，并标明识别结果；未验证 QQ 公告页面控件 |
| 群文件目录 | 用户打开群文件页面，尝试读取已加载的文件名、文件夹及可见元信息 | 文件目录不等于文件正文，需验证子目录、分页、重名及元信息缺失；不自动遍历/下载所有群资料 |
| 群文件正文 | 用户在 QQ 中下载/选择文件，再将指定本地文件交给几微按格式解析 | PDF/Word/表格需要各自解析，扫描图片需要 OCR；只能解析实际取得的文件，不保证过期/删除/无权限文件可恢复 |

这是依据 UI Automation 的控件访问机制提出的分阶段方案，[微软控件模式文档](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-controlpatternsoverview)不构成 QQ 各页面都实现相应模式的保证。优先做当前 QQ 的聊天记录/公告/文件页面兼容性检测；检测通过后再提供读取范围、条数/页数、完整性与失败位置预览，确认后保存同一 data。历史、公告、文件分别记录来源，不能混成没有出处的聊天消息。

对照案例：[NapCat API 文档](https://napneko.github.io/onebot/api)分别列出群历史、公告、根/子目录及文件链接接口，但属于额外协议端路线，不等同普通 QQ 的现成官方接口，也不能从已实现的“接收上报”自动获得这些查询能力。[QQNT_Export](https://github.com/Tealina28/QQNT_Export)的定位是导出已解密数据库，亦不属于单纯登录即可完成的方案。本轮没有采用数据库解密或客户端加载器，没有实际读取、下载真实群资料。

## 当前可以体验的内容

1. 在「插件管理」开启「群消息」（默认关闭），进入左侧同名入口。
2. 添加来源：选择 QQ/微信、手动或对应本机上报方式，填写名称、账号与群标识。手动来源账号选填；实时来源必须填写适配器提供的账号 ID 与群 ID。
3. 包含词逗号分隔，命中任意一个保留；留空保留全部文本。排除词命中任意一个忽略。来源可以暂停，已有消息保留。
4. 手动来源可粘贴完整通知并指定原发送日期。开发者模式显示 QQ/微信虚构示例入口，可重复导入。
5. 收件箱展示原文、发送者、时间和待办建议；日期由简单规则建议，相对日期按消息发送日（上海时区）推算。核对名称及可选截止日期后确认加入待办，也可忽略。消息仅生成候选，不会自动创建待办或修改课表。

当前一条消息对应一个可编辑候选。多事项拆分、周几/时段等完整自然语言理解、附件下载/OCR、撤回/编辑事件、自动改课、系统提醒和全量历史同步尚未实现。

## 本机接收契约

先添加并启用实时来源，再在群消息页面展开「本机接收设置」并开启。默认端口 5274，可改为 1024–65535；占用时换端口。只监听 `127.0.0.1`，每次应用启动都保持停止。开启仅表示接口就绪，不代表平台已登录。

### QQ：OneBot 11

外部 OneBot 登录端配置 HTTP POST 上报：

- 地址：界面显示的 `http://127.0.0.1:端口/onebot`。
- token/secret：界面「查看接入参数」中的本机密钥；NapCat HTTP client 的 token 用于签名。
- 签名：`X-Signature: sha1=<HMAC-SHA1(密钥, 原始 HTTP 正文字节)>`；兼容可信本机桥接的 `Authorization: Bearer <密钥>`。
- `Content-Type: application/json`，正文是标准 OneBot 11 事件对象。仅处理 `post_type=message` 且 `message_type=group`；匹配 `self_id` 与 `group_id`，忽略自发消息、私聊和纯附件。支持消息段数组中的文本及字符串 CQ 文本；不下载附件，也不执行任何回复/快速操作。

### 微信：独立桥接器

当前提供接收协议，**未内置真实 Wechaty/Puppet 登录适配器**。外部受用户控制的适配器将群文本转换为以下对象，再 POST 到界面显示的 `/wechat`，设置 `Authorization: Bearer <密钥>` 与 JSON 类型：

```json
{
  "id": "由平台提供的稳定消息编号",
  "accountId": "适配器登录账号编号",
  "groupId": "适配器提供的 room ID",
  "senderId": "发送者编号",
  "senderName": "显示名称",
  "text": "请在明天前提交报告",
  "sentAt": "2026-10-18T10:30:00+08:00",
  "self": false
}
```

账号、群和消息 ID 应使用字符串；数值仅接受安全整数，避免长编号精度丢失。微信桥接需提供含时区的发送时间，保留原消息 ID，不用每次随机 ID 重放历史。具体 SDK 的 room/message 映射和账号重登录后的 ID 稳定性需随选定适配器验收。

### 回执与失败恢复

接受、重复或不匹配规则返回 204；不匹配的内容不保存。401 是鉴权失败，400 为无效 JSON，415 为非 JSON/浏览器 Origin 请求，422 为事件字段不完整，429 为缓冲已满，503 为本地文件失败。请求上限 128 KiB，文本上限 16000 字；不返回机器人快速操作。外部适配器应在非成功回执后保留原 ID 并稍后重试。

已匹配事件先原子保存到 `data/integrations/chat/pending.json`（最多 200 条），再通知界面。界面提交同一 workspace 快照成功后才确认删除缓冲；重放同一平台/账号/群/消息 ID 不重复创建。新消息到来期间继续处理后续缓冲，核对中的输入保留。工作区最多 50 个来源/500 条消息，满时明确报错，不静默淘汰。已处理记录可手动清理，已加入待办及其证据保留；清理后再次上报旧消息可能重新进入收件箱。

密钥在首次开启时生成，保存到 `data/integrations/chat/receiver-key.json`，业务 JSON 不含密钥；换页隐藏密钥，停止/关闭功能/恢复业务备份/退出应用时停止监听。来源停用或规则变更后，尚未提交的缓冲会按当前规则重新筛选，不匹配项确认移除。JSON 恢复不包含独立密钥与接收缓冲；搬迁整个 data 才包含它们。手动停止不会清空缓冲。

## 验证与后续

本轮使用虚构 QQ/微信事件、本机 HTTP 与实际 Electron main/preload 验证双入口、HMAC/Bearer、账号/群过滤、暂停、连续上报、去重、待办确认、原文安全显示、写入失败、重启和 data 迁移。没有登录真实 QQ/微信；不把协议模拟通过写成真实平台已监测。

下一步是分别选定实际 QQ 登录端与微信适配器，手动登录后对照来源 ID 验收一条真实通知；再补连接健康、撤回/修改事件及多事项拆分。关闭几微只负责关闭本应用的接收器；独立外部登录端由它自己的进程管理，不会强杀用户的 QQ/微信。
