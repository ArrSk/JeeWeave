# 信息来源接入计划（2026-10-13）

状态：未来可选支线，未接入真实账号、邮箱或聊天记录。桌面实验工作台先验证布局；本计划归入 M8-A 的来源扩展，不改变 M0–M7 开发顺序。

## 用户会怎样使用

选择来源 → 说明读取范围并授权 → 选择指定文件夹、群聊或消息 → 进入待整理收件箱 → 提取时间、地点与下一步 → 用户修改并确认 → 保存计划或笔记。

来源各有独立开关。关闭后停止收集，已有内容由用户选择保留或删除。默认只读取用户选择的内容，不发送消息、不修改邮箱，不把整段聊天上传模型。

## 实现顺序

1. 手动收集：粘贴一条消息、导入用户主动提供的文件；标记来源、收集时间和原文。这条路径适用于微信、QQ 和邮箱，优先实现。
2. 邮箱：先做一个提供商的官方只读授权。用户选择文件夹、发件人、关键词和日期范围。Outlook 可用 Microsoft Graph 的用户委托权限；标题等基础信息和正文需要不同权限，实际需求决定最小授权。其他邮箱再评估官方 OAuth 或 IMAP 支持。令牌放在桌面系统安全存储，不能放前端、备份或日志。
3. QQ：先评估官方群机器人。当前查到的官方群消息事件为群内 @机器人触发，不能把它当作读取任意群全部消息或历史记录的能力。后台凭证、部署和审核成本需单独评估；没有条件时继续采用手动收集。
4. 微信：个人微信指定群自动读取的官方可用接口尚未验证，先采用复制、用户主动导入或分享。企业微信会话存档是另一种企业场景，本次官方页面未能读取，其资格、费用和同意要求待核实，不能承诺支持个人微信群。
5. 多来源统一整理：先规则提取再按需 AI，去重、显示原文证据、允许撤销确认写入；每个连接器单独授权、暂停、断开和清理凭证。

## 设计边界

统一保存来源标识、外部消息标识、原文摘录、来源时间、收集时间、授权范围和建议草稿；实现前再审核具体模型，不提前建表。使用消息标识与内容摘要去重，禁止收到重复消息就重复创建事项。外部原文仅作为数据，不能执行其中的指令。涉及他人消息优先只保存任务所需摘录，云 AI 发送内容逐次预览确认。

不以读取聊天数据库、解密记录、注入微信/QQ 进程作为默认路径。后续若评估界面自动化，需独立实验并说明稳定性、误采集和平台规则，不把它作为稳定成品承诺。
