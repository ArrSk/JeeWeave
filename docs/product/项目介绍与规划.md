# 几微 · JeeWeave 项目介绍

本文是几微的项目总纲。以下四项原则适用于各端、各业务插件和比赛特化版本，作为设计、取舍与验收的共同依据。实际交付范围见[交接说明](../HANDOVER.md)。

## 四项长期设计原则

### 一、舒适的交互从第一次使用开始

#### 1.1 先记后理

下课时记一句“找老师问一下第三题”，应当立即可保存，几天后凭“第三题”就能找回。归入高数、补日期、转为待办由用户按需决定。即使一直没有归类，这条记录也应可读、可搜、可编辑。

#### 1.2 简约与可发现性

查看作业时，把原要求、改期和完成放在手边；查来源、关联对象和增加执行时段按需展开。用首次使用者能否发现常用动作、熟练用户能否快速进入深层操作来判断界面是否简约。

#### 1.3 连贯响应与错误恢复

输入后及时显示保存状态，后台分析期间允许继续记录。由周视图进入作业再返回，应保留原来那一周、浏览位置和未保存的草稿。拖错时段、归错对象或误采纳建议，应能纠正或撤回。

#### 1.4 尊重注意力

“周五交报告”是截止要求，“周三晚写半小时”是执行安排，“周五中午提醒我”是提醒偏好。三者可分别修改。错过周三的安排后，用户仍能重新安排执行时间，原截止日期保持准确。

**验收问题**　首次使用者能否独立完成“记录、找回、改期、撤销”？连续使用一周后，今天页是否仍能清楚呈现接下来值得做的事？分别观察输入反馈、页面切换和后台等待。

### 二、对象组织背景，视图服务于不同的问题

#### 2.1 对象保留长期背景

“高数”贯穿一个学期。对象页应让用户从一次课找到布置的作业，从作业回到老师的原要求或自己的解题笔记。数周后，仍能理解当时为什么记录、还有哪些问题待解决。

#### 2.2 按主题、时间和属性审阅

| 用户想知道什么 | 合适的视图 |
| --- | --- |
| 高数最近有哪些事？ | 对象页汇集相关课次、作业、考试和笔记。 |
| 今天接下来做什么？ | 日视图突出当天安排和可执行动作。 |
| 这周哪些事情挤在一起？ | 周视图对照不同课程、项目和个人安排。 |
| 本月有哪些重要节点？ | 月视图突出考试、截止日期和阶段目标。 |
| 周四有哪些课？ | 课程表按节次对齐各科课次。 |

#### 2.3 同一记录保持同一身份，按需支持多重归属

在高数对象里改动作业日期，周视图与月视图应反映同一处修改。长期目标是让一份建模报告同时关联高数和竞赛项目，两处共享原记录与完成状态。一般内容可只关联一个对象，未定日期的内容也可以先留在对象里。

**验收问题**　从日历能否回到作业及其来源？学期结束归档高数后，能否找回笔记，并通过其他相关项目读到同一份报告？后者用于验收未来的多对象关联。

### 三、AI 接受人的自然表达，辅助整理与判断

#### 3.1 理解零碎输入与临时更正

用户可以选取网页段落、群聊消息或随口说一句：“高数第三章下节课前交，哦，最后两题选做。群里说周四可能小测，我没听清。”系统应提取一份注明选做范围的作业，结合实际课次解释“下节课”，把小测留作待核实。输入无需预先整理成模板或标准日期。

#### 3.2 区分事实、推断和不确定性

在草稿中保留原文，说明截止日来自哪句话、哪天由调课记录推算。后续出现正式通知时，帮助用户识别补充、更正和重复内容。普通标签不确定时可以留空；日期歧义会影响提交时，只追问影响决定的细节。

#### 3.3 给出有依据的合理性分析

当两小时的复习被放入四十分钟空档，应指出前后课次、实际可用时长和拆分或改期的选择。缺少任务耗时时，可询问用户或标明估计依据。建议应允许用户修改、拒绝或保留原计划。

#### 3.4 用户掌握写入权与资料边界

分析前让用户看清选中的文字、需要的课表背景和将发往服务端的范围。结果按条采纳，误写可以纠正或撤回。后续建议若与手工修订冲突，应保留用户的选择并指出差异。

**验收问题**　使用含闲聊、转述、相对日期和改口的网页、群聊、口述样本，检查漏提、误判、重复创建和多余追问，并记录用户核对到放心确认所需的时间。现有比赛原型主要按分句与明确日期提取；自然理解、跨来源核对和合理性分析按后续实测确认。

### 四、业务能力按插件设计，共用底座保持精简

#### 4.1 明确不可移除的核心

底座承载稳定引用与数据提交、能力注册与发现、权限和生命周期。评估新职责时，考虑只管理个人项目的用户是否也需要它，并说明由宿主统一承担的理由。课程规则、作业完成条件和提醒触发方式由各自业务拥有。

#### 4.2 通过公共契约协作

处理“下节高数课前交作业”时，课程插件提供下一次实际课次，事项插件写入作业，对象和日历读取同一记录，AI 经用户确认后调用公共接口。新增考试能力时，记录需要改动哪些模块，检查导航、日历和助手能否通过注册信息或已有契约接入。近期优先用可信内置插件验证，第三方插件下载安装与删除另行规划。

#### 4.3 关闭、故障与恢复可预期

关闭 AI 后仍可手工创建作业。课程服务临时不可用时，已有作业仍可读取，关联课次提示暂不可查。插件停用时释放所属资源，重开后检查有无重复注册、重复提醒或重复写入。

#### 4.4 用实际成本优化底座

记录冷启动、输入响应、空闲内存与单插件启用耗时。评估一次真实扩展时，同时记录接入所需修改、资源增量和停用后的回收情况，再决定优化位置。实现边界见[架构说明](../ARCHITECTURE.md)。

**验收问题**　接入一个新业务后，分别关闭、重开并模拟依赖缺失，用户资料是否完整、其他功能能否继续工作、性能变化能否解释？

四个方向共同支撑个人工作台：日常记录积累背景，对象与视图使背景可查，AI 据此提出贴合个人情境的建议，插件契约让这套体验能扩展到学习之外的生活场景。

## 设计初衷

JeeWeave · 几微是本地优先、可通过插件扩展的个人工作台，以对象与事情连接零散信息、时间安排和行动，帮助用户理解来由、推进目标并积累经验。

用户遇到的困难是：课程、作业、笔记和费用分别存放后，需要在脑中重新拼起它们的关系。几微希望保留“为什么做、与谁有关、怎样算完成、今天怎样推进”，让不同入口都能回到同一件事。名字里的“几微”强调细小但重要的日常，“Weave”表示把零散的信息和行动织回相关背景。

课程与学习是首先落地验证的场景，课程表是一个切入口。项目后续也应容纳个人项目、锻炼、旅行及其他生活主题；新增能力是否值得做，取决于是否帮助用户记录、理解或推进事情，不以能否挂在课表下作为条件。

## 内容怎样连接

对象是持续组织相关内容的课程、项目或主题；事情是希望办成的结果；活动是某个时间的一次发生；行动与安排是推进事情的步骤和投入时间。它们通过稳定引用关联，完成状态各自明确，原内容保留一份。详见[对象与事情设计](对象与事情设计.md)。

例如“提高身体素质”可以关联篮球课程、每周锻炼安排与训练笔记；未来的相关支出也可由记账能力接入。完成一次锻炼不会自动完成这个长期主题。多对象关系、记账等仍属于后续设计，不因例子出现就视为已实现。

用户可以从一段想法、一份资料、一个事项或一次活动开始。无需先建对象、填目的或拆步骤；笔记、独立待办、无日期内容和待归类资料始终可单独使用。

## 底层怎样支持

宿主统一插件运行、依赖、公共接口、事件、导航与资源清理；数据机制维护原记录、稳定身份、持久化和恢复。业务插件分别负责课程、事项、笔记、提醒等能力，通过公共服务连接。今天、日历与对象视图汇集原内容，不再维护一套同名记录与完成状态。

AI助手是调用公共能力的可选入口，先拟草稿再确认执行；不用AI仍能手动完成核心操作。平台层处理Windows、Android及浏览器各自的文件、窗口和系统能力。职责和实际边界见[架构说明](../ARCHITECTURE.md)。

## 当前基础与后续边界

Windows 0.4.0已有课程表、教务导入、统一事项、今天、日历、笔记、对象Beta、查找、全局助手和独立提醒，内置业务已接入插件宿主。对象当前主要支持手动主归属，不代表完整多对象网络。

Android已有Beta包，最新版桌面能力已移植至本地源码预览；等待体验确认，APK尚未随之更新。Web/PWA仍是独立客户端，资料不会自动跨端同步。真实系统输入、后台通知与旧设备兼容需要分别验收。

记账、完整知识库、多对象关系、跨设备同步和安全安装第三方插件等仍为后续方向。群消息接入继续暂停，保留原代码与资料。内置插件可开关不等于已经具备第三方插件安全沙箱。

## 最终愿景与开发约束

让用户能沿着“原始信息 → 相关对象 → 要办成的事 → 行动与时间安排 → 今天的推进 → 结果与经验”理解和处理日常，也允许内容只停留在记录或参考阶段。

底座为各插件提供稳定、流畅的连接，电脑和手机按场景设计布局。本地优先、旧资料兼容、失败不覆盖与用户可控制保持不变；视觉方案继续由用户主导。先把具体流程做顺，再扩展能力，避免强制分类和重复模块。

近期安排见[路线图](../ROADMAP.md)，笔记设计见[笔记流程](随记功能与开发流程.md)，底座参考见[插件化设计](../design/插件化底座与迁移流程.md)。愿景不表示上述能力已全部完成，也不授权立即打包或发布。
