# 几微 AI 开发维护文档

这份文档写给后续接手项目的开发代理，也写给需要快速判断改动影响的人。它不是产品宣传文案。所有“已完成”都必须以源码和实测为准，路线图里的内容不能直接当成成品。

## 接手前必须做的事

1. 先读 `AGENTS.md`；
2. 再读 `docs/HANDOVER.md` 的最后一节和未修复问题；
3. 查看 `git status`，不要覆盖用户已有的未提交改动；
4. 需要理解产品方向时读 `README.md`、`docs/项目介绍与规划.md` 和 `docs/ROADMAP.md`；
5. 需要改模型或边界时读 `docs/ARCHITECTURE.md` 和 `docs/DECISIONS.md`。

## 当前真实产品边界

当前用户指定的开发主线是桌面端，网页端独立维护。`desktop/` 已有独立界面、课程管理和南邮 WebVPN 直接抓取导入；后者已由用户确认课程信息正确，不再把桌面端仅描述成网页外壳。历史平台交付顺序见 [ROADMAP 的平台开发路线](ROADMAP.md)，不能据此将当前桌面任务改为网页任务。APK 尚无实现；没有 Mac 和 Apple 开发者权限时，不把 `.ipa` 或 Apple 原生能力写成近期承诺。

当前可用重点是课程表、今天、计划、待办、模块开关、本地保存、备份和示例数据。记账、笔记、AI 是预留模块。不要在能力列表、README 或交接文档中把占位页描述成可用功能。

核心产品判断是“今天工作台”：每个新功能都要说明它如何帮助用户知道今天先做什么。新增入口前先检查是否能作为今天页的卡片、筛选条件或下一步行动呈现。

## 新增技能参与开发的方式（2026-10-09）

新下载的技能作为按需工具加入流程，不会自动改变现有技术栈、目录或检查命令。每次接手先看 `AGENTS.md`、`HANDOVER.md` 和当前 `git status`，再根据任务选最少的一组技能。

| 任务 | 使用的技能 | 进入时机 | 结果要求 |
| --- | --- | --- | --- |
| 查 React、Vite、Tailwind、Electron、SDK、API、CLI 或云服务用法 | Context7 | 先 `resolve-library-id`，再针对单一概念 `query-docs` | 记录库名、版本、查询范围和对代码的影响 |
| 页面重做、交互改进、响应式和可访问性 | Impeccable | 需要实际改界面时作为主流程 | 先读当前页面与设计资料，再做小步修改并完成桌面、窄屏检查 |
| 聚焦某个用户体验问题 | ui-ux-pro-max | 需要可操作的 UX 证据时 | 用最小范围检索，结论必须能落到具体页面或组件 |
| Tailwind、表单、弹窗、响应式组件实现 | ui-styling | 已确定界面方案后 | 复用现有 `shared/packages/ui` 和样式；不因技能示例安装 shadcn 或迁移框架 |
| 跨页面颜色、字号、间距和状态统一 | design-system | 发现重复样式或 token 不一致时 | 先整理现有 token，再补语义层和组件层，避免无需求地搭新系统 |
| 品牌语气、Logo、宣传文案或视觉资产 | brand / design | 产品宣传或品牌任务 | 保留已确认的几微名称和视觉方向，变更需有明确任务依据 |
| 横幅、封面、Hero 图或广告素材 | banner-design | 用户确实需要一张宣传图时 | 只生成素材，不把宣传图流程混入日常页面开发 |
| 产品介绍或路演 HTML 演示 | slides | 需要演示稿时 | 交付独立演示文件；PPTX 仍走 `presentations` 技能 |

### 实际执行顺序

1. 先写清目标页面、用户动作和验收现象；规划阶段不运行界面改造技能。
2. 涉及第三方库时，先核对仓库中的实际版本，再执行 Context7 查询；每个查询只问一个概念。
3. 需要改 UI 时，读取当前实现、`README.md` 和相关设计记录，使用 Impeccable 做主流程；其余 UI 技能只补对应环节。
4. 以最小改动实现目标，保持 `core`、`data`、`ui`、`platform`、`web` 分层和现有数据兼容。
5. 按改动范围运行检查。代码改动仍需 `pnpm typecheck`、`pnpm test`、`pnpm build`、`pnpm smoke`；纯文档改动检查 UTF-8、链接、`git diff --check` 和 diff。
6. 把真实结果、未验证边界和工具可用性写回 `docs/HANDOVER.md`，不得把技能建议或规划写成已完成能力。

## 代码分层纪律

- `shared/packages/core` 只放纯模型和纯函数，不依赖浏览器、React、Dexie 或文件系统；
- `shared/packages/data` 负责仓储、Dexie、备份、学期和作息服务；
- `shared/packages/ui` 只放跨模块通用 UI 和模块契约；
- `shared/packages/platform` 负责通知、文件、持久化等设备能力；
- `web` 负责 React 页面、外壳和模块装配；
- 页面通过 `useJiwei().repos` 和 data 服务读写，禁止直接使用 Dexie；
- 功能模块之间不要互相导入；跨模块共享逻辑放到 core、data 或 shared；
- 时间和周次计算只能复用 core；
- `refresh()` 只增加 `dataVersion`，不会自动重建课次；写入课程、学期、作息或调整后按需调用重建。

## 数据安全规则

- `Block` 是模板，`Occurrence` 是派生结果；编辑课程应保留原 `id` 和 `createdAt`；
- 正常课和调入课是 `normal`，调出课是 `moved`，停课是 `cancelled`；是否上课使用 `isOccurrenceActive()`；
- 备份恢复要先校验日期、引用和派生课次，再提交数据；失败不能覆盖原数据；
- 恢复后要同步 Zustand 中的选中学期和页面状态；
- 删除学期或课程时要检查调整、提醒、笔记等引用；
- 不改变旧备份字段、ID 规则和相对路径配置，除非同时提供兼容迁移；
- 模块关闭只隐藏入口，不删除已有数据。

## 计划、待办和今天的长期方向

不要继续维护两套互不相干的事项数据。统一事项模型至少需要考虑：

- `status`：收件箱、下一步、进行中、已完成、已归档；
- `priority`：用户可理解的优先级；
- 时间规则：截止日、日期区间、每周重复、无期限；
- `sourceId`：来自课程、导入、AI 或用户手动输入；
- 可选的课程、项目、空间关联。

迁移时先保持旧 `Block` 数据可读，再逐步让计划页、待办页和今天页共享服务层。不要为了“统一”一次性破坏现有用户数据。

## AI 开发边界

AI 的第一阶段是候选内容生成器，不是自动写库机器人：

1. 接收用户主动提供的文字、图片或文件；
2. 生成带来源和置信提示的候选课程、事项或账目；
3. 在界面上展示预览和可编辑字段；
4. 用户确认后调用现有导入/保存服务；
5. 记录可撤销的写入结果。

AI 失败、无网络或额度用尽时，手动录入仍必须可用。不得把个人课程表或账目静默上传到第三方服务，也不得在没有用户确认时覆盖已有数据。

## UI 和交互维护规则

- 首页优先展示今天、当前/下一节和需要执行的事项；
- 功能很多时使用分组、开关和渐进展开，不把所有按钮平铺；
- 输入框至少保留手机可用的触控尺寸，避免 iOS 输入时页面缩放；
- 弹层有明确关闭方式，关闭按钮固定但不遮挡内容；
- 页面切换保留轻量过渡，并尊重减少动态效果设置；
- 未开放功能必须显示“尚未开放”及预计阶段，不要让用户误以为按钮失效；
- 示例数据必须可重复导入，不能每次点击都复制一套数据。

## 每次代码改动后的验证

在仓库根目录依次运行：

```powershell
pnpm typecheck
pnpm test
pnpm build
pnpm smoke
```

涉及交互、恢复、刷新、离线或手机布局时，还要做浏览器验证，并在 `docs/HANDOVER.md` 写明是否覆盖了真机。纯文档改动至少检查 UTF-8、链接和 `git diff --check`。

## 记录和提交纪律

- 用户没有授权时不推送 GitHub、不部署、不使用 `pnpm save`；
- 不改写历史交接记录来掩盖旧问题；
- 每次完成后在 HANDOVER 追加日期、改动、检查结果和未验证边界；
- 产品能力变化同步 README/ROADMAP；模型或关键选择同步 ARCHITECTURE/DECISIONS；
- 报告结果时先说用户能看到的变化，再说技术实现和验证结果。
